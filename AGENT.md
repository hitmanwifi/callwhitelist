# Call Whitelist — рабочие правила агента

## Назначение

`org.alexrust.callwhitelist` — локальное Android-приложение для фильтрации входящих вызовов через `CallScreeningService`. Правила, журнал и настройки хранятся на устройстве; сетевой обмен и аналитические SDK не используются.

## Текущая архитектура

```text
app/                  # MainActivity, Compose UI, navigation, system helpers
callfilter/           # CallScreeningService и горячий путь решения
core/model/           # Kotlin/JVM модели предметной области
core/database/        # Room entities, DAO и database provider
core/preferences/     # DataStore настроек пользователя
core/designsystem/    # Material 3 theme
data/                 # Room/DataStore/snapshot реализации
domain/               # чистые правила фильтрации и тесты
docs/                 # продуктовые и будущие privacy/open-source документы
```

Отдельный Gradle-модуль для каждого экрана не создаём. Каждый экран и крупный компонент — отдельный Kotlin-файл; навигация остаётся в пакете `navigation`.

## Обязательные технические правила

- Пакет приложения: `org.alexrust.callwhitelist`.
- Новый код только Kotlin. Java-исходники не добавлять.
- Исходники должны находиться в `src/main/kotlin`, `src/test/kotlin` или `src/androidTest/kotlin`; `src/*/java` не допускается даже как пустой source root.
- Для `kotlin.time` и времени календаря использовать `kotlin.time`/`kotlinx-datetime`, не `java.time`.
- Все версии зависимостей и плагинов задавать только в `gradle/libs.versions.toml`.
- Compose и Material 3 выравнивать через BOM.
- Пользовательские тексты хранить в `values` и `values-en`; хардкодить UI-тексты нельзя.
- Material icons брать только из стандартной библиотеки Material Icons.
- Горячий путь `CallScreeningService`: локальный snapshot, без UI/сети/ожидания DataStore; `respondToCall` должен выполняться до журнала, уведомлений и другой фоновой работы.
- Не добавлять `READ_CALL_LOG`/`WRITE_CALL_LOG`: журнал приложения не должен превращаться в доступ к системному Call Log.
- Контакты и call metadata считать персональными/чувствительными данными: запрашивать минимальные разрешения после понятного disclosure и хранить локально.
- Не добавлять workaround для OEM-логов без воспроизводимого пользовательского симптома.

### Важное пояснение по отображению `java` в Android Studio

Для чистых Kotlin/JVM-модулей `core:model` и `domain` Android Studio может показывать логическую группу `java`, хотя физический путь исходников — `src/main/kotlin`. Источником истины является файловая система и Gradle source set. Аудит обязан проверять оба: физические пути и отсутствие `.java`/пустых `java`-каталогов.

## Правило проверки после каждого этапа

После каждого этапа обязательно:

1. Обновить этот файл: отметить этап и текущий статус.
2. Проверить каждый модуль из `settings.gradle.kts`, а не только `app`.
3. Проверить `src/main`, `src/test`, `src/androidTest`: `.java = 0`, пустых source/package-каталогов нет.
4. Проверить отсутствие `com.example`, старых package-путей, `java.time` и ссылок на удалённые модули.
5. Запустить compile/test-задачу каждого применимого модуля.
6. После структурных изменений выполнить clean-сборку и повторный аудит.
7. Только после успешной проверки сделать отдельный git-коммит этапа.

## Статус baseline

- Проект состоит из 8 модулей: `app`, `callfilter`, `core:model`, `core:database`, `core:preferences`, `core:designsystem`, `data`, `domain`.
- Debug APK и доменные тесты ранее собирались успешно.
- Фактических Java-исходников сейчас нет; требуется сохранить это состояние при переработке.
- `core:model` всё ещё содержит модели в одном `CallModels.kt` и должен быть разбит по файлам.
- Git-репозиторий создан, но на момент составления плана не содержит коммитов и настроенного remote.
- Текущий `targetSdk` — 35; перед публикацией нужно перейти минимум на API 36 с учётом требования Google Play с 31.08.2026.

### V1. Устранить дублирование журнала

- Использовать `Call.Details.getCreationTimeMillis()` как стабильное время события вызова для API 26+.
- Добавить идемпотентную вставку в Room: повторная доставка одного вызова не должна создавать вторую строку.
- Защитить проверку и вставку транзакцией; корректно обрабатывать скрытый номер.
- Не терять существующий журнал при изменении схемы: если потребуется версия Room, добавить явную migration, не полагаться на destructive migration.
- Покрыть повторную доставку и два разных вызова одного номера тестами.

Статус V1: реализация завершена, компиляция всех 8 модулей и аудит пройдены; ожидает отдельного коммита.

### V2. Глобальный тумблер «Фильтрация включена»

- Добавить отдельную настройку фильтрации, не смешивая её с системной ролью.
- Передавать состояние в версионированный snapshot; при выключении сервис разрешает вызовы и не применяет пользовательские блокирующие правила.
- Добавить тумблер в «Обзор» и «Политики» с единым состоянием.
- Системная роль остаётся отдельным статусом: предупреждение и CTA показывать только если приложение не назначено обработчиком вызовов.
- Добавить тесты snapshot/evaluator для включённого и выключенного режима.

Статус V2: реализация завершена, тест выключенного режима, сборка и аудит всех модулей пройдены; ожидает отдельного коммита.

### V3. Единый UX статуса и статистики

Статус V3: общая статусная карточка и Material Icons для статистики добавлены; warning роли показывается только без системной роли; сборка и аудит пройдены.

### V4. Временные разрешённые номера
